# IELTS PEEL Skill 全面质量审计

审计日期：2026-07-26

## 一、结论

IELTS PEEL Hacker 已经是一个有辨识度、可运行的内部原型，但距离可以稳定为付费客户服务的 IELTS 学习产品仍有明显差距。

| 评估面 | 得分 | 当前阶段 |
|---|---:|---|
| 可移植 Agent Skill | 43/100 | 可用原型，命令和方法论存在漂移 |
| 测试与评估体系 | 24/100 | 不能作为可靠质量裁判 |
| 生产环境准备度 | 28/100 | 不应公开、多用户部署 |
| 商业辅导能力 | 27/100 | PEEL 段落工具，不是完整辅导产品 |
| 综合客户服务准备度 | 31/100 | 内部 Alpha |

距离受控商业 Beta（70 分）约差 39 分；距离较强的客户级产品（85 分）约差 54 分。

最关键的判断是：当前问题不在于 UI 是否漂亮，也不在于提示词是否更长，而在于产品的信任基础还不成立。

## 二、五个发布阻断项

### 1. API Key 可能被转发给任意地址

`server/index.js:49-105` 接收用户传入的 `baseUrl` 和 `apiKey`，`server/utils/llmClient.js:6` 使用二者创建带认证信息的客户端。

这意味着攻击者可以让服务器将 API Key 发送到攻击者控制的地址，或请求内网服务。

必须改进：

- 公开模式不允许请求方任意设置 `baseUrl`
- 改用服务器配置的 Provider Profile
- 如保留自定义 Provider，只允许明确的 HTTPS 白名单
- 拒绝本地、内网、链路本地、带凭据及重定向后的危险地址
- 增加网络超时、取消和出口限制

### 2. 所有匿名用户共享个人记忆

客户端固定发送 `userId: 'default'`，服务器又信任请求中的 `userId`。Wizard 回答会以 JSON 形式落盘，并进入后续提示词。

公开部署后可能出现：

- 用户 A 的经历进入用户 B 的回答
- 用户可污染其他身份的长期记忆
- 个人信息无法删除、导出或设置保留期

必须改进：

- 未完成认证和租户隔离前，关闭公开持久化记忆
- 用户身份必须来自服务端认证会话
- 只保存经确认的结构化事实，不保存原始长文本
- 增加同意、保留期、删除、导出、加密和审计
- 使用原子、并发安全的持久化方案

### 3. 当前 Quality Gate 会把劣质内容判为通过

`validator.js` 主要检查标签、禁用连接词、部分因果词、具体名词和句子数量，并不验证论证是否相关、成立、真实、通顺。

已发现的错误通过场景包括：

- P/E1 只有非常空泛的短句，E2 放两个具体名词就可能通过
- 荒谬或虚假的事实可能通过“物理性”检查
- 标签重复或顺序错误可能被解析器掩盖
- 多句 Layer 仍可能通过
- 验证失败后，接口仍可能返回 `ok: true`

必须改进：

- 使用严格结构化 Schema
- 强制 P、E1、E2、L 各出现一次且顺序固定
- 四句模式下每层严格一句
- 校验题目相关性、立场一致性、因果充分性、E1-E2 对应、L-P 回扣、事实风险和语言质量
- 修复失败后返回 `quality_failed`，不得继续标记成功
- 用人工标注数据测量 precision、recall 和 false-accept rate

### 4. `/score` 不是 IELTS 官方意义上的评分

`aiScorer.js` 让模型扮演 IELTS examiner，并给 P/E1/E2/L 打 1-9 分，但这不是官方评分维度。

Writing 官方维度包括：

- Task Response
- Coherence and Cohesion
- Lexical Resource
- Grammatical Range and Accuracy

Speaking 还有独立的流利度、词汇、语法、发音维度。

必须改进：

- 立即将当前 `/score` 定位为“PEEL 结构反馈”
- 删除 examiner 和预测 Band 的表达
- 明确提示这不是官方 IELTS 分数
- Writing 和 Speaking 使用不同反馈模型
- 未经合格教师盲评校准前，不展示 Band 预测

### 5. 题库来源和商业使用权不清楚

题库只说明来自本地 PDF warehouse，缺少版权所有者、授权、使用范围、审校记录和更正历史。项目的 MIT License 不能自动覆盖可能来自第三方的题目内容。

必须改进：

- 在权利明确前，从公开和商业产物中隔离题库
- 建立来源、所有者、取得日期、授权、允许用途、审校人、更正记录
- 代码 License 与内容 License 分开
- 用自有、合法授权或可公开使用的题目替换高风险内容

## 三、其他高风险差距

1. `SKILL.md` 声明五个命令，但权威系统提示词只实现三个命令，Web Runtime 又是第三套行为。
2. 模型输出为空或格式错误时，修复流程可能不触发。
3. SSE 会先显示未验证答案，再追加修复答案；重试还可能造成内容重复。
4. Wizard 原始回答被提升到 System Prompt 的高信任层，形成持久 Prompt Injection 风险。
5. Agent 自己生成失败后，系统会把失败记成“用户弱点”。
6. 所有回答被强行压入四句 PEEL，容易训练模板依赖，而不是可迁移能力。
7. README 和模板容许编造例子，同时使用“empirical evidence”式权威表达，容易教出虚假论证。
8. 根构建依赖多个独立安装，并在构建时写用户主目录；Tailwind 路径也导致生产 CSS 不完整。

## 四、与真正客户级 Skill 的能力差距

真正可服务客户的 IELTS Skill 至少需要：

| 能力 | 当前状态 | 客户级要求 |
|---|---|---|
| 用户诊断 | 基本没有 | 当前水平、目标分数、考试日期、诊断样本 |
| 官方维度反馈 | 未实现 | Writing/Speaking 分开，基于官方标准 |
| 练习闭环 | 偏向直接给答案 | 尝试、提示、反馈、修改、比较、复习 |
| 个性化 | 文件记忆且不隔离 | 认证身份、确认事实、可删除、可追溯 |
| 进度跟踪 | 几乎没有 | 保存版本、错误趋势、掌握度、下一步建议 |
| 内容可信度 | 来源不明、断言偏激 | 有来源、条件、反例、审校和许可 |
| 评估可靠性 | 2 个 golden case | 至少 300 个分层案例及人工校准 |
| 生产可靠性 | 本地 Playground | CI、监控、备份、回滚、超时、支持流程 |
| 隐私与安全 | 不满足多用户要求 | 认证、租户隔离、最小化、删除、加密 |
| 无障碍 | 部分基础能力 | WCAG 2.2 AA、键盘、语义、动态播报 |

## 五、值得保留的部分

1. 卫星/无人机/显微镜/回归的抽象层级比喻有记忆点。
2. Skill-first 的分发方式有价值，适合 Agent 平台安装。
3. 离线确定性质量检查是正确方向，只是当前规则太浅。
4. Topic、Model、Entity 数据可作为后续人工审校的原料。
5. 生成后编辑和重新验证可以发展成真正的修改学习闭环。
6. 现有 26 个快速测试可以作为新评估体系的起点。

## 六、建议重新定义产品

建议将首个可靠版本定义为：

> 一个双语 IELTS 论证发展教练，帮助学习者生成、诊断、修改并迁移段落推理能力，同时明确区分 PEEL 训练与 IELTS 官方评分。

首个版本不应宣称：

- 完整 IELTS Tutor
- IELTS Examiner
- 可靠 Band Predictor
- 未经来源确认的“真实考试题库”

## 七、全面提升路线图

### Phase 0：止血和信任修复（1-2 周）

1. 封锁任意 Provider URL 和 SSRF。
2. 关闭共享记忆，或实现认证和租户隔离。
3. 将 `/score` 改为 PEEL 结构反馈，删除 Band 暗示。
4. 解析或验证失败时返回 `quality_failed`。
5. 隔离来源不明的题库。
6. 限制 CORS、Metrics 和可信代理设置。
7. 增加上游超时、取消和稳定错误码。

验收标准：

- SSRF/API Key 转发安全测试全部通过
- 跨用户记忆访问测试全部拒绝
- 无无效结果返回 `ok: true`
- 所有产品表面不再声称官方 Examiner 或 Band 分数
- 未授权内容不进入公开构建

### Phase 1：建立可信 Skill Core（2-6 周）

1. 为所有命令建立 Request/Response Schema。
2. Sync 和 SSE 共用同一执行管线。
3. 从一个命令注册表生成 Skill、Runtime、Help 和测试。
4. 为每个命令定义可执行输出合同。
5. Wizard 改为明确状态机，只保存用户确认的事实。
6. 修复 Topic Routing，支持边界、歧义和多主题。
7. 建立真实 CI 和构建漂移检查。

验收标准：

- 100% 拒绝缺失、重复、乱序、畸形标签
- 首次命令合同通过率 >=95%
- 一次修复后通过率 >=99%
- Skill、Runtime、README、测试之间零命令漂移

### Phase 2：从生成器变成学习产品（6-12 周）

1. 增加目标分数、当前水平、考试时间和语言偏好的 onboarding。
2. 增加 `practice`、`hint`、`model`、`compare`、`revise` 模式。
3. 分开 Writing Task 2 和 Speaking Part 3 的训练设计。
4. 基于官方维度提供形成性反馈，但暂不预测 Band。
5. 保存版本化的原稿、反馈和修改稿。
6. 对 Topic 内容做来源、偏见和文化适配审校。
7. 完成隐私控制和 WCAG 2.2 AA 修复。

验收标准：

- >=70% 试点用户提交修改稿
- >=60% 用户在修改稿中解决目标问题
- 100% 反馈包含：对应维度、原文证据、问题、下一步动作
- 无障碍审计无 Critical 问题
- 删除和导出流程端到端通过

### Phase 3：商业 Beta（12-20 周）

1. 建立至少 300 条分层评估语料。
2. 邀请合格 IELTS 教师进行盲评。
3. 测量命令遵循、错误通过、幻觉、评分一致性和修改提升。
4. 建立监控、备份、回滚、事故响应、分析和客户支持。
5. 完成商标、宣传、隐私和内容许可审查。

验收标准：

- Validator precision >=95%，recall >=95%
- False accept rate <=1%
- Topic routing macro-F1 >=0.90
- 展示 Band 前，人工评分 MAE <=0.5，weighted kappa >=0.70
- 可用性 >=99.5%，请求完成率 >=98%
- p95 反馈延迟 <=15 秒
- 安全、隐私、无障碍无 Critical 问题

## 八、优先顺序

1. API Key、安全与用户隔离
2. 纠正评分和营销声明
3. 严格 Parser 与 fail-closed Quality Gate
4. 单一命令注册表和事实来源
5. 测试及评估 Harness
6. 内容来源、偏见和方法论修复
7. 尝试-反馈-修改的学习闭环
8. 生产基础设施、无障碍、分析和客户支持

现阶段不建议优先增加更多 Topic、扩大题库、继续美化 UI 或扩写 Prompt。这些工作会扩大风险面，但不会解决信任基础。

## 九、最终判断

当前项目大约完成了客户级产品所需工作的三分之一。概念值得继续投入，但必须从“自信地生成和打分”调整为“透明地训练、验证和修改”。

最高杠杆的一项改进是：

> 用严格、类型化、失败关闭、经数据验证的 Coaching Contract，替换当前宽松 Parser/Validator 和 Examiner 风格评分。

这会同时改善输出可靠性、测试质量、学习者信任、安全边界和商业可辩护性。
